# Contributing

## Development setup

Clone the repository and install dependencies:

```sh
git clone https://github.com/a4amk/agy-agent-mcp
cd agy-agent-mcp
npm install
```

Node 22.6 or later is required. The shipped server is plain compiled JavaScript (`npm run build` -> `dist/`, which is what `bin/mcp.mjs` and `bin/follow.mjs` run - Node refuses to type-strip files under `node_modules`), while the repository's own test scripts (`node test/client6.ts`, `node test/client.ts`) execute the TypeScript sources directly through Node's type stripping, which is what needs 22.6+. The server runs the CLI headlessly, so no `tmux` is needed. You only need an authenticated Antigravity CLI (`agy`) in your PATH if you want to run the maintainer-level live end-to-end test (`node test/client.ts`).

## Running from source

Start the server locally over stdio:

```sh
npm run start
```

## Linting and formatting

Formatting and linting are enforced with [Biome](https://biomejs.dev/) `2.5.15`, configured in `biome.json` (2-space indentation, double quotes, semicolons, `lineWidth: 120`, default branch `main`):

```sh
npm run lint       # biome check src test bin
npm run lint:fix   # biome check --write src test bin
```

## Running tests

Run the offline test suite and linter before submitting changes:

```sh
npm test               # offline suite (node test/client6.ts — no agy auth or quota needed)
node test/client.ts    # live e2e (maintainer-level: requires agy auth + a trusted workspace)
```

`npm test` (`node test/client6.ts`) uses fake shell scripts and runs completely offline for free — covering argv envelopes, `stream-json` output parsing and `.stream` rendering, idle and opt-in wall-clock timeouts (`kind: "idle"` vs `"wall"`), git-based `files_touched`/`scope_violations` auditing, the startup `.ndjson`/`.stream` retention sweep, `watch_task` helpers (including that a finished run's watch report carries the complete final result, so a failed run reports why it failed), the progress bridge (a foreground delegation streams progress frames, a detached one emits none), the ignored-cancel hint (a cancel for a run this process does not own is reported as ignored, while a cancel that works and a cancel for a finished run carry no hint), the drain on a client disconnect (a detached run survives it and its receipt carries the result, while an abandoned foreground call is still killed), and the MCP-layer effort/model resolution, failure surfacing, input validation and discovery error reporting.

`node test/client.ts` is a maintainer-level live end-to-end check that runs real headless turns through `agy` (blocking `general_task`, conversation resume, and `watch_task`) against a trusted workspace and consumes a small amount of model quota.

## Continuous integration

GitHub Actions (`.github/workflows/ci.yml`) runs `npm ci`, `npm run lint`, and `npm test` on Node 22 for pushes to `main` and all pull requests.

## Releasing

- A release is a **tag on `main`**. The tag push is what publishes: `.github/workflows/publish.yml` runs on the push of a `v*` tag, publishes the package to npm through Trusted Publishing (OIDC, no token) and creates the GitHub release. There is no manual trigger - to retry a failed release, re-run the workflow run of that tag push. npm refuses to publish the same version twice, so a run that failed *after* the publish (the GitHub release step) cannot be re-published: create that release by hand from the tag.
- The preparation of a release is **one command**, not three hand-edits:

  ```sh
  npm run release -- 0.3.0
  ```

  It does the whole prep in one go and refuses to do it half-way:
  - **the release notes come first** - the script refuses to run unless `CHANGELOG.md` carries a `## Unreleased` section (and it is not empty): the maintainer writes the notes of the release there *before* running the command, and the release publishes exactly that section;
  - **the version is validated** as a **stable `MAJOR.MINOR.PATCH`** - three numbers, no leading zero (e.g. `0.3.0`) - and nothing else: no prerelease and no build metadata. A prerelease would need the workflow to publish with `--tag` (npm refuses a prerelease without it) and npm strips build metadata at publish time, so either way the published version would not be the version the tag names. The version in `package.json` is therefore exactly the version npm publishes and exactly the version the tag names; it must also be newer than the current `package.json` version;
  - **the working tree must be clean** - the script refuses any pre-existing modification, so it always starts from a known state;
  - it then edits exactly four things: the `version` in `package.json`, the two version fields in `package-lock.json` (the top-level `version` and `packages[""].version` - the lockfile is bumped with the version, or it would claim an older version than the package), the `## Unreleased` heading in `CHANGELOG.md` (renamed to `## <version> - <date>`) and the `serverInfo.version` of the two goldens `test/goldens/initialize.json` and `test/goldens/duplicate-initialize.json`. The goldens are compared exactly by the test suite, so they can no longer drift away from `package.json` (they sat at `0.1.2` through two releases before);
  - it runs the gates (`npm test` and `npm run lint`) and aborts without committing if either fails;
  - the whole sequence is **all-or-nothing**: a write error, a signal, a red gate or a failed commit puts the working tree back the way it was, so a failed run never leaves the tree half prepared and never blocks the next run;
  - it creates the commit `chore(release): <version>` with those files and nothing else.
- The script **never pushes, never tags and never publishes** (it has no network access at all): it prepares the commit, the maintainer does the rest.
- The flow, end to end:
  1. write the release notes under `## Unreleased` in `CHANGELOG.md` and commit them;
  2. `npm run release -- <version>` - prepares the version bump, the changelog heading and the goldens, runs the gates and creates the `chore(release): <version>` commit;
  3. push the branch, open a PR into `main` and merge it with **Rebase and merge** (a squash merge would collapse the history; a merge commit is rejected by the linear-history rule);
  4. on `main`, tag the release and push the tag:

     ```sh
     git tag v<version> && git push origin v<version>
     ```

     That tag push runs `.github/workflows/publish.yml`, which publishes to npm through Trusted Publishing (OIDC, no token) and creates the GitHub release.
- The workflow refuses to publish unless:
  1. **the ref is a release tag** (`refs/tags/v<version>`) - a branch ref, or a tag that is not a version, is refused;
  2. **the tag matches the `package.json` version** (`v0.3.0` publishes `0.3.0` and nothing else) - a mismatch is refused, so a tag can never publish a version other than the one it names;
  3. **the tagged commit is on `main`** (`git merge-base --is-ancestor`) - a release cut from a side branch is refused.
- The npm trusted publisher must name the workflow file `publish.yml` **and** the GitHub environment `release`. npm puts the publish token into the OIDC token only when the job declares that environment, so the job declares `environment: release`; without it the publish is refused - npm rejects the token (*Unable to authenticate*, or a 404 *package not found*, depending on the npm CLI version).
- The release notes of the GitHub release come from the CHANGELOG: the `## <version>` section of the released version, plus a `**Full Changelog**` compare link against the previous release tag. The section is built before `npm publish`, and a missing or empty section fails the release - a release without its notes is not published.
- The job runs `npm ci`, `npm run build --if-present` and `npm test` before publishing, so a red suite blocks the release.
- The workflow runs from the tagged commit, so `publish.yml` has to be on `main` before the first release.

## Pull requests

- Target the `main` branch and keep pull requests focused on a single change.
- Use [Conventional Commits](https://www.conventionalcommits.org/) for commit messages:
  - **Subject**: `<type>(<scope>): <imperative summary>`, lowercase after the prefix, no trailing
    period, at most 72 characters. Allowed types: `feat`, `fix`, `docs`, `refactor`, `perf`,
    `test`, `build`, `ci`, `chore`, `revert`.
  - **Body**: required whenever the subject alone does not explain *what changed and why*.
    Separate it from the subject with one blank line, wrap it at 72 characters, and prefer prose
    over bullet lists. Explain the motivation (the bug, the contract that was broken) before the
    implementation details.
  - **Footer**: optional `BREAKING CHANGE:` notes and issue references, separated by a blank line.
  - One logical change per commit; do not mix a fix with an unrelated refactor.
- When adding or modifying delegation tools (`general_task`, `explore_task`), inspection tools (`watch_task`), or discovery tools (`list_models`, `list_agents`), add an entry to the five-tool table in `src/index.ts` (title, description, hand-written `inputSchema` literal, and handler); the `test/goldens/` files capture the exact wire shape and must stay in deep agreement.
- Make sure `npm run lint` and `npm test` pass cleanly before opening a pull request (and `node test/client.ts` when changing live CLI integration).

## Behavioral reference

### Input validation (the advertised schema is enforced)

- The hand-written `inputSchema` literal of each tool in `src/index.ts` is the **single source of truth**: the validator (`validateArgs`) reads that literal, it never re-declares a rule in a second place. Honoured keywords: `type`, `enum`, `minimum`, `maximum`, `minLength`, `minItems`, `items.type`, `pattern`, `required`, and `additionalProperties: false`.
- All five tools validate their arguments: the two delegation tools, `watch_task`, and the two list tools (which take none, so any key is an unknown argument).
- A refused call returns the house envelope - a single `{"error": "..."}` key with `isError: true` - and the message **names the offending argument** (`missing required argument: prompt`, `prompt must be a string, got: number`, `timeout_ms must be <= 3600000, got: 999999999`, `unknown argument: totally_bogus ...`). It is produced through the same code path as the runner's own `cwd` / `edit_scope` refusals.
- A refused call spawns nothing: no `agy` process, no `.stream` / `.ndjson` transcript, no progress notification, and leaves the server state clean.
- `prompt` must be a non-empty, non-whitespace string (`minLength: 1` plus the `pattern: "\\S"` in the schema). The accepted ranges are otherwise unchanged: `timeout_ms` `0..3600000`, `tail_lines` `0..2000`, `effort` `low|medium|high`, `edit_scope` `minItems: 1`.
- The `effort must be one of low|medium|high, got: ...` message is produced on the MCP tool surface by exactly one place - the validator, from the schema's `enum` - and its text is unchanged. (The follow CLI has its own `--effort` usage message; it is a different surface, not a second MCP validation path.)

### Delegation result fields (`general_task` / `explore_task`)

- `task_id` (`task_<8-hex-chars>`) — names both `<AGY_MCP_STATE_DIR>/<task_id>.ndjson` (`transcript_file`) and `<AGY_MCP_STATE_DIR>/<task_id>.stream` (`stream_file`), and is accepted directly by `watch_task` (`stream_file`).
- `status` — `"success"` (exit code `0` and CLI `status: "SUCCESS"`), `"timeout"` (killed by the idle timer or opt-in wall ceiling via `SIGTERM` then `SIGKILL` after 5s), `"quota_error"`, or `"error"`.
- `prompt` — echoed prompt, truncated to 200 characters (`…[truncated N chars]`).
- `cwd` — resolved working directory (validated under `AGY_MCP_ROOT` when set).
- `opencode_session_id` — echoed when OpenCode attaches `ai.opencode/sessionID` (`ses_...`) in request `_meta`.
- `response` — CLI response text, truncated to the **last 20,000 characters** when longer (with `response_truncated: true`).
- `response_empty` (`true`) and `response_empty_note` — attached when `status === "success"` but `response` is empty or whitespace, reminding the caller to check `denied_actions`, `files_touched`, and `notes`. It marks a *silent success* only: a run that produced no output because its tool requests were auto-denied is re-classified as a failure (see "A blocked run is not a success" below) and carries an `error` instead.
- `duration_seconds` — taken from the CLI `result` event, falling back to measured wall-clock seconds when omitted; `num_turns` and `usage` are forwarded when reported by the CLI.
- `conversation_id` and `resume_hint` — resumable Antigravity conversation UUID when reported by the CLI.
- `denied_actions` — tool invocations auto-denied by headless mode; `auto_approve_applied` (`boolean`) is always present to record whether `--dangerously-skip-permissions` was actually passed.
- `notes` — all non-JSON stdout lines plus stderr (stream-event lines excluded), capped at **4,000 characters**. The one exception is a `result` event the runner could not use (its `result` is not an object): its **raw line** is kept in the notes, so the caller sees exactly what the CLI printed.
- `files_touched` and `scope_violations` — git porcelain diff before vs. after the run when `cwd` is inside a git work tree, each capped at **50 entries**. `edit_scope` is an audit-and-replay control (the CLI writes files directly without prompting, and `--sandbox` only walls terminal commands); entries escaping `cwd` or `AGY_MCP_ROOT` are rejected before spawn.
- `exit_code`, `error`, and `quota_note` — `exit_code` is the process exit code and is recorded for every run (`0` on success, `null` when the process was signalled); `error` is populated on every failed run, with one exception: a run the CLI reported as `SUCCESS` that is only re-classified as `quota_error` afterwards keeps the CLI's success wording and carries `quota_note` instead of an `error`; `quota_note` on quota-classified runs. `error` is chosen case by case, and the list of wordings is exhaustive:
  - `task was cancelled before execution started` (cancelled before the spawn);
  - `failed to spawn <bin>: <message>` (the child could not be started at all);
  - `child idle for <ms>ms; killed (SIGTERM first, SIGKILL after 5s)` (the idle timer);
  - `task exceeded hard cap of <ms>ms; killed (SIGTERM first, SIGKILL after 5s)` (the opt-in wall ceiling);
  - `task was cancelled` (cancelled in flight);
  - the CLI's own failure message **verbatim** when its `result` event reported one (the process exit code then stays in the separate `exit_code` field);
  - the process-level fallbacks: `agy exited with code <n>` / `agy exited with signal <s>` when the process itself failed (with the `(no JSON result line in output)` hint when there was no JSON result), `agy reported status <STATUS> and exited 0` when the CLI reported a non-`SUCCESS` status, `agy exited 0 without reporting a result status (the run failed)` when the result event carried no usable status, `agy exited 0 without producing a result event (the run failed; no JSON result line in output)` when there was no result event at all, and `agy exited 0 but its result event was not usable (the run failed; the CLI printed a result event whose "result" was not an object)` when a result event *was* printed but the runner could not use it (a JSON line was printed, so the "no JSON result line in output" wording would be a lie — the same reason applies to the `agy exited with code <n>` fallback, which then carries the same reason instead of that hint);
  - a composed suffix `(agy reported: <cli message>)` appended to a server-side cause (a spawn failure, a kill, a cancellation) when the CLI reported an error of its own — the CLI's message is appended, never dropped;
  - the blocked-run wording: `the sub-agent was blocked: its tool request (<action>) was auto-denied because headless mode cannot prompt for permission, so the run produced no output. Re-run with auto_approve: true, or add an allow-rule under permissions.allow in your own Antigravity settings.json (e.g. command(<target>)).` — the denied action(s) are named (see "A blocked run is not a success" below).
- A run the server classifies as a failure is never described as a clean exit: none of the server's own failure wordings contains `code 0` (a CLI message that says so itself is still surfaced verbatim).
- **Tool envelope**: a delegation whose `status` is not `"success"` is returned with `isError: true` (both the foreground and the background path agree); a successful run and a `"running"` background handle are returned with `isError: false`.
- **Model and effort resolution** (part of the call contract, not a result field): `effort` accepts `low|medium|high` — the only levels the available models accept; anything else (e.g. `xhigh`, `max`) is refused locally, before anything is spawned. Without an explicit `effort`, `general_task` runs at `medium` and `explore_task` at `low`. A model id that already carries a tier (`gemini-3.8-flash-high`, as returned by `list_models`) takes precedence over that default: its tier is already encoded in the id, so no `--effort` flag is passed next to it, and pairing it with a *different* effort is refused locally as well (the `agy` CLI rejects that combination outright). Local refusals come back as the standard `{"error": "..."}` envelope with `isError: true`, spawn no task, and leave the server state clean.
- **Trimmed id arguments**: `model`, `agent`, `project` and `conversation_id` are trimmed before they are used — the `agy` CLI compares them verbatim, so `" gemini-3.8-flash "` is an unknown model — and the trimmed value is what reaches the CLI *and* what the error messages quote (e.g. the tier/effort conflict message names `"gemini-3.8-flash-high"`, not the padded form). A value that is only whitespace becomes empty and is treated as absent (there is no such id). `prompt` is **not** trimmed (leading whitespace may be meaningful) and `cwd` is untouched (the runner resolves it).

### A blocked run is not a success (the CLI's own condition)

- **The gate**: a run is **blocked** when the CLI reported `denied_actions` (a non-empty array) **and** the response is empty. That is exactly the condition under which the `agy` CLI itself prints *"no output produced - a tool required the `<x>` permission that headless mode cannot prompt for, so it was auto-denied"* — the server repeats the CLI's judgement instead of inventing one. The CLI still reports `status: "SUCCESS"` for such a run, so the server has to say what the CLI only put in its note.
- **Where the classification lives**: in `runTask` (`src/agy.ts`), so the durable receipt carries it and `watch_task` inherits the verdict from the receipt — there is no second implementation in the MCP layer. It runs **after** the quota upgrade, so a quota failure stays `quota_error`, and it only ever turns a *successful* run into `"error"` (a run that already failed keeps the CLI's own message).
- **The error message** names the denied action(s), says that headless mode cannot prompt for permission, that the run therefore produced no output, and how to fix it: `auto_approve: true` on the call, or an allow-rule under `permissions.allow` in the user's own Antigravity `settings.json` (e.g. `command(<target>)`).
- **No false positives**: a run that had a denial but still produced a response stays a success, and a run with an empty response and **no** denial stays a success (with `response_empty`). `denied_actions` and the CLI's own note in `notes` are never dropped.
- **`response_empty` is not set on a blocked run**: that field marks a *successful* run that stayed silent. A blocked run carries the `error` instead, so the two signals never overlap.
- **The residual risk**: the gate cannot tell "the agent did the work but said nothing and hit an incidental denial" from "the agent was blocked" — a run that did the work and stayed silent is reported as a failure. `files_touched` (the git audit) shows that the work happened. This is the price of matching the CLI's condition; the alternative (inventing a richer judgement) would report failures the CLI never reported.

### Orchestrator contract (the result is a summary; the transcript stays on disk)

- **One call returns the whole report**: a foreground `general_task` / `explore_task` awaits the run and answers with the complete `TaskResult` in that single call (`runDelegation` awaits `runTask` and returns its result - `src/index.ts`), so the caller polls nothing and spends no extra call on it. The detached path (`background: true`) exists to *start* a run and collect it later, and it costs that extra call: the handle is answered immediately, and the run's result is then only reachable through `watch_task` or the `.ndjson` receipt on disk.
- **The result is the summary, not the transcript**: it carries the sub-agent's final `response` plus the facts an orchestrator needs - `status`, `usage`, `files_touched` (when `cwd` is a git repo), `scope_violations` (when `cwd` is a git repo **and** `edit_scope` was given), `error`, `exit_code`, `conversation_id`, `resume_hint` - measured at about **1 200 characters (~300 tokens)** of JSON for a realistic run. The transcript length does not land in it: `response` keeps the **last 20 000 characters** (`MAX_RESPONSE_CHARS`; `response_truncated: true` marks the cut), `notes` is capped at **4 000 characters** (`MAX_NOTES_CHARS`), `files_touched` / `scope_violations` at **50 entries** each, `prompt` at 200 characters.
- **The transcript is on disk, never in the result**: `transcript_file` (the `.ndjson` machine log) and `stream_file` (the human-readable `.stream` mirror) are *paths* in the result - no transcript text is carried in it.
- **`watch_task` is the on-demand detail channel, not a second way to get the result**: the caller already has the summary, and pulls the detail - the transcript tail (`content`, bounded by `tail_lines`: default `400`, `0` = all lines, hard cap 200 000 characters) and the step digest (`steps`, a bounded window over the 50 most recent steps) - only when it needs it. Every poll costs the caller exactly what it pulls.
- **The progress bridge is the only in-call streaming channel MCP offers, and it is thin**: `notifications/progress` is the protocol's only spec-compliant way to stream during an in-flight tool call (a `tools/call` returns exactly one `CallToolResult` - MCP has no streaming tool responses), but a frame carries the newest **mirrored lines** - step markers and the lines a step has *completed* - not the live narration: `onStreamLine` counts only newline-terminated lines (`bridge.buffer` in `progressBridgeFor`), so a narration chunk in flight is carried only once its line is terminated. The narration is written to the `.stream` file as it is produced (`mirrorEvent` -> `mirror(su.text_delta)` in `src/agy.ts`) and is available live through `watch_task` / the `.stream` file in every client.
- **Whether the client shows the frames is the client's business**: OpenCode discards `notifications/progress` (its MCP client installs a no-op `onprogress` handler), Claude Code renders it since v2.1.153 (2026-05-28, `anthropics/claude-code#51713`). A server cannot assume the frames are rendered, so the `.stream` file and `watch_task` are the client-independent channels.

### Discovery tools (`list_models` / `list_agents`)

- **The command**: both tools run their helper through `runCmd` (`src/agy.ts`) with a 30 s timeout — `agy models` and `agy agents`, never anything else.
- **Three failure modes, never collapsed**: `runCmd` reports *how* the command ended — `"spawn"` (it could not be started at all, e.g. a missing binary: ENOENT), `"exit"` (it ran and exited non-zero, with the code) or `"timeout"` (it never finished; the limit is named). A timeout used to be reported as exit code `127`, which was indistinguishable from a missing binary; it is a timeout now.
- **A failure is an error, not a result**: a failed discovery command answers with the standard `{"error": "..."}` envelope (`isError: true`, one key). The message names the command (`agy models` / `agy agents`), the failure mode and the exit code when there is one (e.g. `` `agy models` failed: exited with code 7 ``), and keeps the captured output **inside** the message (`output: …`) so nothing the CLI printed is lost. The crash output is never presented as the result: a failed call carries no `models` / `agents` field.
- **Success is not an error, even with no output**: a command that exited 0 is answered with `isError: false`. `list_models` returns `models` (the raw output; when the CLI printed nothing the field reads "(no output from `agy models`)"), `model_ids` (the parsed ids) and — when the output yielded no id at all — a `note` saying the output could not be parsed into ids. `list_agents` returns `agents` (or "(no custom agents configured; default agent will be used)" when the CLI printed nothing).
- **What a silent `agy agents` does NOT prove**: `agy agents` prints nothing on many installations, so `list_agents` cannot distinguish "no custom agents are configured" from "the CLI changed its output format" — the tool reports what the command printed, not the state of the agent set. Do not document (or rely on) that wording as a fact about the installation; the `agent` argument stays undiscoverable while the CLI stays silent.
- **Parsed model ids**: `parseModelIds` (`src/agy.ts`) treats a line of the CLI's output as an id when it contains a TAB; the id is the text before the first TAB. Lines without a TAB (e.g. the `Fetching available models...` header) are not ids. `models` keeps the raw text unchanged — `model_ids` is additive.
- **What `agy models` actually lists**: the CLI only prints tier-carrying ids (`gemini-3.8-flash-high`), never a bare id such as `gemini-3.8-flash`. A bare id is still a valid `model` argument (it takes its tier from `effort`), it simply does not show up in the list — so `list_models` is not a complete catalogue of the ids the server accepts, and `model_ids` is exactly what the CLI printed, unfiltered.
- The discovery tools take no arguments: an unknown argument key is refused by the shared schema validator (`{"error": …}`, `isError: true`, nothing spawned), exactly like every other tool.

### `watch_task` report and `.stream` format

- `stream_file` input accepts an absolute path under `AGY_MCP_STATE_DIR`, a bare `task_<id>.stream` filename, or a task ID (`task_<id>` / `<id>`); omitting it selects the newest `task_<id>.stream` by mtime. Paths escaping `AGY_MCP_STATE_DIR` throw.
- Returns `found`, `file`, `bytes`, `modified` (ISO timestamp), `running` (`!finished`), `finished` (whether a line starting with `== done:` is present or a result event exists in the `.ndjson` receipt), and `content` (last `tail_lines` lines, default `400`, `0` = all lines, hard-capped at the last **200,000 characters** with `clipped: true` and a leading `…\n`).
- **Digest**: every report that found a transcript also carries a compact step feed parsed from the transcript - `steps` (one entry per completed event: `kind` `read`/`write`/`run`/`phase`, `label`, `target`, `dur_seconds`, `output`, `total_tokens`, `thinking_tokens`), `step_count`, `phase` (last phase marker), `elapsed_seconds` (from the `== done:` marker) and `usage_latest` (newest step usage). The digest is a **bounded window**: `steps` holds at most the 50 most recent steps (oldest -> newest inside the window, `MAX_DIGEST_STEPS` in `src/agy.ts`) while `step_count` reports the **total** number of steps, so the clipping is self-evident (`step_count > steps.length`) and a long run does not blow up the report. Clients render the digest for a live status display and read `content` only for detail; `result_ready` is `true` once the durable receipt carries the final result (the `== done:` line lands slightly earlier, before the server finishes the file-scope audit). A report that found no transcript carries no digest and no result fields at all: exactly `found` and `candidates` for the no-argument form, and `found`, `file` and `candidates` (plus `hint` when the `.ndjson` twin exists) when a `stream_file` was given.
- When the watched task has finished, the report returns the **complete** final result — every field of the durable `.ndjson` receipt (the same shape `general_task`/`explore_task` returns: `status`, `response`, `error`, `notes`, `exit_code`, `usage`, `conversation_id`, `num_turns`, `denied_actions`, `quota_note`, `files_touched`, `scope_violations`, `resume_hint`, `progress_bridge`, …), read durably across sessions and processes. A failed run therefore reports *why* it failed, not only that it failed. The watch-owned fields (`found`, `file`, `bytes`, `modified`, `running`, `finished`, `result_ready`, `content`, `content_len`, `steps`, `step_count`, `phase`, `elapsed_seconds`, `usage_latest`, `clipped`, `hint`, `candidates` — the single source of truth is `WATCH_OWN_FIELDS` in `src/agy.ts`, and the compiler refuses a watch field that is missing from it) always win: the receipt is stripped of exactly those names before it is merged, so even a tampered or foreign receipt cannot overwrite them. The conditionally-set ones (`phase`, `elapsed_seconds`, `usage_latest`, `clipped`, `hint`, `candidates`) stay **absent** — the key is not present at all — when the transcript does not carry them. While the task is still running there is no receipt yet, so the report carries no result fields at all. Passing `cancel: true` stops a running detached task (kills the child through the runner's abort path and returns the final report showing the run cancelled). The cancel path lives in the MCP layer's in-flight delegations registry, so it is **in-process**: a run the caller names is looked up by `stream_file`/task ID, while omitting `stream_file` cancels the run only when exactly one delegation is in flight (if several are in flight the cancel is ignored and the report's `hint` notes the ambiguity). A detached run started by another server process cannot be cancelled from here, and the report says so instead of pretending the cancel worked — the `hint` field carries the note that the cancel was **ignored** (the run is in flight, but it is not owned by this server process; only the process that started it can cancel it). The hint is set only when the cancel was ignored *and* the run is still running: a cancel that works and a cancel for an already finished run carry no hint (`finished: true` already says there was nothing to cancel). The two `hint` uses never collide — the missing-`.stream` twin hint is on a not-found report, the cancel hint on a found one. For an orchestrator the watch report is the **on-demand detail channel**, not a second way to get the result: the delegation call already returned the summary, and a poll costs the caller exactly what it pulls (`content` bounded by `tail_lines`, `steps` a bounded window over the 50 most recent steps).
- When `found` is `false`, returns up to 5 recent `candidates` (`task_<id>.stream`, newest first) and a `hint` pointing to the `.ndjson` machine log if a twin `task_<id>.ndjson` exists without a `.stream` file.
- `.stream` rendering maps `init` to `session open · cwd=<cwd> · permission_mode=<mode> · tools=<n>`, `step_update` to `● user_input`, `● agent_response` (with flowed `text_delta` chunks and `  ⎿ done in <dur>s · <total_tokens> tokens[ · thinking <thinking_tokens>]`), and directional tool markers (`→ Read|View|Grep|List <target>`, `← Write|Edit <target>`, `$ <command>`, or `● <name>[ <target>]` followed by `  ⎿ [<output> · ]done in <dur>s`), closing with `== done: status=<status> · <dur>s` on `result`. A `result` event whose inner `result` is not an object gets `== result event: unusable (the CLI printed a result event whose "result" was not an object)` instead — the transcript says so, so a live watcher is not blind, and the raw line goes to the run's `notes`.
- **The receipt must be a plain object**: `readNdjsonResult` accepts a `result` event only when its `result` is a plain object. `typeof [] === "object"`, so an array (or any other non-object) used to pass as a receipt and its elements surfaced in the watch report as the numeric keys `"0"`, `"1"`, …; it is not a receipt now, so the watch report carries no result fields for it.

### Quota detection, lifecycle, and logs

- **Quota detection**: when a run fails (`status !== "success"`) or returns an empty response, `error`, `response`, and `notes` are scanned against quota/rate-limit patterns (`quota`, `rate limit`, `429`, `resource exhaust`, `credit`, `billing`, `usage limit`, `daily limit`, `fast forward`, `model capacity`). Matches upgrade `status` to `"quota_error"` and attach `quota_note` instructing the caller to inform the user rather than silently falling back to another agent.
- **Machine logs & retention**: a run logs `task_start`, `spawn` (or `spawn_error`), `timeout` (`kind: "idle" | "wall"`), `exit`, `audit`, `task_end` and — last — the `result` event, which carries the complete `TaskResult` receipt that `watch_task` reads back, to `<AGY_MCP_STATE_DIR>/task_<id>.ndjson` (a run cancelled before it started logs an `abort` event instead of a `spawn`; a run killed with the server can lose its `result` event to the exit race, so "the receipt is always there" is not a guarantee). At startup, `sweepStateDir()` removes `task_*.ndjson` and `task_*.stream` files older than `AGY_MCP_RETENTION_DAYS` (default `7`; `0` disables).
- **Shutdown**: `shutdownRunner()` sends `SIGTERM` (and `SIGKILL` after 1.5s) to all in-flight child processes so orphaned runs do not burn model quota in the background. That covers the delegation child **and** the discovery child: `runCmd` registers its `agy models` / `agy agents` process in the runner's child registry (`activeChildren`) and leaves it when it settles, so a hanging discovery command is reaped on the way out instead of surviving the client. (The 5s SIGTERM-then-SIGKILL window belongs to the *run's own* idle/wall kill, not to the shutdown path.) A **client disconnect** (stdin EOF/close, or an unhandled `EPIPE` on a broken pipe) reaps the children that have no reader at once and then drains the detached runs (the next bullet); a **`SIGINT`/`SIGTERM`** never drains: it kills every child — the detached ones included — and exits at once.
- **A detached run survives the client disconnect (the drain)**: `background: true` detaches the run from the *tool call*, not from the *client*. When the MCP client disconnects (stdin EOF/close, or an `EPIPE` on a broken pipe) while a **detached** run is in flight, the server does **not** kill it: `shutdownAndExit` waits for that run's promise (`drainDetachedRun` in `src/index.ts`), so the server stays alive until the run ends, the run's receipt is written, and only then does the server exit. The result is then collectable from **any** client that can see `AGY_MCP_STATE_DIR` (`watch_task` with the task id). An abandoned **foreground** call is the opposite case — nobody will read its answer, so it is killed on the disconnect exactly as before.
- **What is reaped when, and what is exempted**: the children **without a reader** are reaped **at once**, before the drain — an abandoned foreground call's child and a hanging discovery command (`agy models` / `agy agents`) die at the disconnect, exactly as they did before this behaviour existed. The runner knows which child belongs to a detached delegation: `TaskOptions.detached` marks that child's registry entry (`activeChildren` in `src/agy.ts`), and the disconnect path calls `shutdownRunner({ keepDetached: true })`, which skips the detached delegations' children. Every other shutdown path (`SIGINT`/`SIGTERM`, and the final reap after the drain) calls `shutdownRunner()` without the exemption and kills every child, the detached ones included.
- **The two cases, told apart by the in-flight delegations registry**: detached runs are marked `detached` and their promises kept there, and only detached runs are drained.
- **The cost**: the drain ends when the run ends, and the run's idle timer resets on every byte it produces — so a **productive** run can keep the server alive for as long as it runs (the idle kill only fires after 15 minutes of silence, and the hard wall cap is opt-in: `AGY_MCP_PRINT_TIMEOUT_MS`, default off). `SIGINT`/`SIGTERM` is the only escape: it kills every child and exits the server at once, so a drain can never be used to keep the process alive against an operator's signal.

### Concurrent delegations and progress notifications

- **Concurrent delegations**: any number of delegations may run at once; a second delegation is no longer refused or queued. Each in-flight delegation is tracked in the server's module-level registry keyed by JSON-RPC request id, visible to cancellation and shutdown paths. Each concurrent delegation runs as an independent child process with its own stream transcript, durable ndjson receipt, and result envelope. The cancel path acts on the run the caller names via `stream_file`/task ID (or cancels the run if exactly one is in flight; multiple in-flight runs without `stream_file` are ignored with an ambiguity hint). On client disconnect, the drain awaits every detached run concurrently so all receipts are written before the server exits.
- **Progress bridge**: only for delegation calls that carry a client-provided `params._meta.progressToken` (absent token = byte-for-byte today's behavior). It is event-driven from the single mirrored `.stream` append site in the runner (fired in the same event-loop turn as the file write), coalesces emissions to at most one `notifications/progress` every ~200 ms with an unref'd timer, and carries a monotonic counter of completed mirrored lines (`progress` starts at `0` with the `task started · stream <basename>` notice; `total` is omitted as unknown). Each message holds the last up to 2 mirrored lines, clipped to 160 chars per line / 400 chars whole; a synchronous final flush always writes the last lines (including the `== done: ...` marker) to the client **before** the result envelope for that call, while a shutdown (SIGINT/SIGTERM/EOF) mid-run may leave the last flush unwritten (acceptable). What a frame carries is the newest mirrored lines - step markers and the lines a step has completed - not the live narration (a narration chunk is counted only once its line is terminated); the narration reaches the `.stream` file and `watch_task` instead. Whether the client renders the frames at all is up to the client: OpenCode discards them (no-op `onprogress` handler), Claude Code renders them since v2.1.153.
- **Detached runs get no progress bridge**: a `background: true` delegation answers immediately with a handle, so the request it belonged to is no longer in flight and `notifications/progress` has nothing to attach to (the official MCP SDK client drops its progress handler when the response arrives and then reports `Received a progress notification for an unknown token` for every later frame). The `background` flag is therefore read **before** the bridge is created, and a detached call creates no bridge at all: no frames, no `progress bridge active` log line, no `progress_bridge` field in the run's receipt, and nothing from the detached run's `finally`. A `_meta.progressToken` on such a call is ignored (not an error, not echoed); `watch_task` is the detached run's progress channel.

### Live-follow companion CLI (`agy-agent-follow`)

- **Follow CLI contract**: `bin/follow.mjs` → `dist/follow.js` calls `runTask` directly (same bridge hooks as the server, no MCP layer, no JSON-RPC): stdout carries the `--- task <id> · stream <name> ---` banner, then the live mirrored `.stream` transcript lines as they are written, then the `=== task done ===` marker and the final result JSON (exit code `0` only on `status: "success"`); stderr carries the `[agy-agent-follow] tool=<tool> model=<model|default> cwd=<cwd>` meta banner (plus the problem lines and the usage text on a usage error, and the runner's message when the run throws). `--effort low|medium|high` sets the reasoning tier (the levels the available models accept); a model ID that already carries a tier (`gemini-3.8-flash-high`) must not repeat a *different* one — that combination is refused locally (exit code `2`) before any task is spawned, because the `agy` CLI rejects it. `--tool general|explore` pins the same `accept-edits` / `plan` modes as the MCP tools; Ctrl-C (exit 130), SIGTERM (exit 143), and EPIPE kill the in-flight child via `shutdownRunner()`.

## Deliberately not implemented

These are decisions, not gaps. Each was considered and rejected on purpose — do not "fix" one without a product decision.

- **No concurrency cap**: the number of concurrent delegations is bounded by the machine and the account's quota, not by the server; the caller is free to fan out.
- **No MCP task API**: the server advertises `execution: { taskSupport: "forbidden" }` on every tool — the MCP task protocol is not offered. It is the spec-idiomatic async design, and it is what a server with long-running calls should advertise. But a client can only use it when it advertises the `tasks` capability — **OpenCode does not**. A task-based server would therefore, in practice, only make an orchestrator *poll* — more calls, more tokens, more context — for no gain over the handle-and-watch workflow this server already has (`background: true` + `watch_task`).
- **No async delegation mode** (a tool call that answers "still running, ask again"): the orchestrator contract is **one call → the complete result** (~300 tokens of context, the whole `TaskResult` in a single `tools/call`). An async rewrite puts exactly that asset at risk — the caller pays an extra round trip plus the polling context to get the same report — and it would take away the reason this server exists. The detached path covers "start now, collect later" without touching the foreground contract.
- **No `cancel_task` tool**: `watch_task(cancel: true)` already stops a run this process owns, and it *reports* a cancel it could not honour instead of pretending it worked. A second tool would duplicate that surface (and the MCP cancellation semantics) without adding a capability.
- **No cross-process cancel**: the cancel path acts on the in-flight delegations registry, so it can only stop a run this server process started. Cancelling a run owned by another process needs PID signalling plus an identity check (the PID must be proven to be that run's, not a recycled one) and a "cancel requested" marker the owning process polls — a feature, not a bug fix. Until that exists, an ignored cancel is reported as ignored (the report's `hint`).
